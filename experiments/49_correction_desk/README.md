# Experiment 49: the Desk, a correction backend for about 300 correctors

**Question** (owner, 2026-10-21). Experiment 48 mapped the "Web of Science" direction. Every next step there
(fixing groupings, identity work on the authority file, metrics) produces decisions that need somewhere to land.
Before more linking, what should the correction backend be? It should look clean and professional, like AI-Search's
`/admin-vdb`.

**Answer so far (draft 1, 2026-10-21, design only, nothing built).** [DESIGN.md](DESIGN.md):

- **A decision editor, not a database editor.** Every correction is an append-only decision (who, when, why, the
  evidence seen) keyed to stable ids. It sits on a "people's sheet" over the machine's reading and is re-applied on
  every build. A decision whose key vanishes is flagged as orphaned and is never dropped silently.
- **"No" is stored too** ("not the same person"), so the linker never re-merges what a person split.
- **Three domains:**
  - **page:** patches43's operations, unchanged;
  - **metadata:** D33, with the printed form kept;
  - **identity:** person, cited work, back reference, institution, journal. Each has positive and negative
    operations, and each of experiment 48's error kinds maps to one.
- **The task queue:**
  - tasks are generated by detectors, one per probe-D workload row;
  - they are ordered by impact × uncertainty and routed by skills;
  - each task is leased so no two people take the same one.
- **Trust:**
  - gold tasks, about 5%, measure accuracy;
  - a sample goes blind to a second corrector, and disagreements go to an editor;
  - each decision kind has its own review rule.
- **Releases:** the machine reading plus all accepted decisions, then checks. Metrics are computed only on
  releases.
- **The stack:** PostgreSQL, a FastAPI API and Next.js + Tailwind screens in the admin-vdb style. The screens are
  Overview, Work, entity pages with history, Review, Team, Releases and Activity.
- **Build order:** P0 design → P1 backend on the 600 → P2 screens → P3 pilot with 5–10 correctors → P4 scale to
  300.
- **The owner's answers** (DESIGN.md §13, 2026-10-21):
  - catalogue errors go out as a list and are never written into the catalogue;
  - all correctors are equal; each owns their corrections; others leave notes, and they settle it between themselves;
  - the languages are Arabic, English and French;
  - the team works remotely, so a separate server with HTTPS;
  - the Desk has its own accounts.

**Mockup** (static and clickable; private link): https://claude.ai/artifact/G6MZZ6zVz9sm6KfstRuKrj, copy at
`out/desk_mockup.html`. It has three screens:
- **Overview:** tiles and the queue by kind;
- **Work:** the «الديوان» card from experiment 48, eight real citations to be grouped into books;
- **History:** of that work.

Queue sizes, people and history are made-up examples. The page is marked as such.

## P1: the backend prototype (2026-10-21)

**Built and passing.** Done means three things (DESIGN §12), and each is now a test that passes:
- **(a)** a rebuild from scratch reproduces every decision;
- **(b)** a "not the same" decision survives a linker run;
- **(c)** orphaned decisions are detected.

There are no screens yet (P2). Everything runs on 127.0.0.1 and in PostgreSQL 16 (database `inkdesk`, schema
`desk`). `platform_v2.db` is only ever opened read-only. Nothing was changed in experiments 43, 47 or 48, or in
`src/`.

**The review model was changed by the owner during the build** (2026-10-21; DESIGN §7 is to follow):
- **One key.** A decision is accepted as soon as its corrector makes it. `review_rules` stays a per-kind setting,
  and every kind is set to `single`. No second-key or tie-break flow is built.
- **Ownership.** A decision's owner is its actor. Only the owner, or an `admin`, can supersede or revert it.
  Anyone else gets a 403 that names the owner. Deciding the same question again on the same subjects is refused
  the same way.
- **Notes instead of disagreement handling.** A corrector who disagrees leaves a note on the decision. The owner
  sees it under `/me/notes`.
- **Gold** is a quiet accuracy gauge, shown to admins only. It never changes what happens to a decision.

**The release step** builds a release without touching `platform_v2.db`:
1. The reading is copied through SQLite's backup API, because the reading has a live 150 MB WAL. The copy goes to
   `/home/appuser/data/desk/releases/<release_id>.db`.
2. Decisions are applied in phases (page, metadata, identity, back references) and, within a phase, in the order
   they were made. Each one goes inside a savepoint.
3. After each decision, every constraint laid down by the decisions applied so far is checked again:
   - **must-link:** a `same_*`, a split group, `confirm_work`, `link_byline`;
   - **cannot-link:** a `not_same_*`, the groups of a split.

   So a person's decision holds whatever the linker joined or split.
4. Each decision gets an outcome in `applications`: applied | superseded | orphaned | conflict.
   - **conflict:** a decision that would break another person's earlier one is rolled back. The earlier one
     holds. Both owners get a note and the later owner gets a task.
   - **orphaned:** a decision whose key has vanished is applied in no part. Its subject is marked orphaned and its
     owner gets a re-anchor task.
5. The release copy describes itself:
   - retired ids go to its `merged_ids` (asserted by `person`);
   - every decision becomes a `patches` row (source `person`, priority 1) with a `patch_applications` row.
6. Checks: `PRAGMA foreign_key_check` (0 before and 0 after), counts before and after, every applied decision
   re-checked on the final state, and a sha256 fingerprint of the 15 tables a decision can touch. The fingerprint
   leaves out clocks.
7. At most 2 release copies stay on disk. Only copies this tool registered are deleted.

**Stable keys** (DESIGN §2):
- `work:C…`, `person:A…`, `mention:<mention_id>`, `authority:<id>`;
- `byline:<anchor_key>` (for the 95 bylines with no ink anchor: `<stem>|<block>|<pos>|<script>`);
- `pubfield:W…|field` and `line:…`, reserved for P2+.

These were measured, not just assumed. A full `link47.py` run on a copy, in test (b), left the set of active card
ids, the person ids and the shown mention ids **identical**. Every current key matches its pattern. Four mention
ids carry a note id instead of a word span (0694 has no anchor), and the pattern allows for them.

### The detectors on the 600 (machine reading)

| task kind | found | rule | machine's guess |
|---|---|---|---|
| work joined without an author | 62 | probe B: a card cited by 2+ articles with author-less members | `split_work` by author group when the members print 2+ disjoint author sets (uncertainty 0.9), else `confirm_work` (0.4) |
| possible same work | 154 | probe B's under-merge rules, ported from `under_cands.py` | `same_work` / `not_same_work`, from the rule's measured share in probe B's sample: stripped-equal 0.9, contained 0.82, similar 0.25 |
| byline twin | 22 bylines in 12 articles | probe C: a provisional byline beside the catalogue-only contributors of the same record | the contributor whose heading words the byline carries, by the same word or by `translit_pairs` (share ≥ 5%) |

- **The byline-twin guesses.** All 7 guesses read right. Examples: «Khalid Talal Alotaibi» → «العتيبي، خالد طلال»,
  «Abbas A. Al-Mejren» → «المجرن، عباس علي», «طه حسين» → «سلامة، طه حسين علي». Initials and roles («ع. م»,
  «المفتى العام») get no guess.
- **Ordering.** Priority = impact (citations or works moved) × uncertainty.
  - The diwan card scores 18.9.
  - The top task is «البحر المحيط» at 27.0.
- **Routing.** Skills route each task: `ar`, or `en|fr` for a Latin name, which either reader can do.
- **Settled subjects.** A detector creates no task for a subject that has a standing decision. An undo (revert or
  retire) is not a standing answer, so after one the question can be asked again. Open tasks a detector no
  longer finds are marked stale.
- **Cost.** All three detectors take 1.8 s and 65 MB.

  A second build gave an identical fingerprint and identical applications.
- **(b) A "not the same" survives a linker run.**
  - `link47.py --db <copy> --work <tmp>` took 47 s and re-joined the diwans on one card. The ids were unchanged.
  - Then a future linker joining the "not the same" pair was simulated, the way an under-merge rule would join
    it: the members were moved onto one card, with a `merged_ids` row.
  - The release built from that copy applied 5 of 5. The split and the merge hold. The kept-apart card is active
    again and its retirement row is gone.
- **(c) An orphaned decision is detected.**
  - An `unresolvable` decision was made on «B Hansem, op.cit.» (0852). Then its mention id was shifted in the copy
    (`w203-207` → `w203-208`), as a re-extraction would shift it.
  - The release did not crash: 5 applied, 1 orphaned. The subject is marked orphaned, and an `orphaned_decision`
    task is reserved for the decision's owner.
  - The owner answered the task on the new key. The next release shows the old decision superseded and the new one
    applied. 2 copies are on disk.
- **Ownership:**
  - (i) a corrector's revert, supersede or same-question decision on another's decision → 403, naming the owner;
  - (ii) an admin's revert → 200, and the original is superseded;
  - (iii) Bob's note on Alice's decision appears in Alice's `/me/notes` and not in Bob's. Alice resolves it.
- **Append-only:** UPDATE of the payload or the note, DELETE, TRUNCATE and a backwards status move are all refused
  by the database (`restrict_violation`).
- **Conflict between two owners:**
  - Bob's `same_work` would re-join two of Alice's split groups. In the release it is a `conflict`, and Alice's
    split holds.
  - Both get a note, and Bob gets the task.
  - Alice cannot answer Bob's task. Bob retires his own decision.
- **Detectors:** 62 / 154 / ≥11 found. After Bob decides the Muqaddima pair and the Alotaibi twin, their tasks
  close and a re-run makes none.
- **Queue:**
  - tasks are served by skill, highest priority first;
  - a held task is served to its holder again and never to another person (409);
  - after `skip` a task is not served again to that person; after `unsure` it goes to someone else, with the note.

### Decided on the way (not in the brief)

- **`confirm_work`** was added for "the machine is right: one work". It pins the card's members together and stops
  the task from returning.
- **Twins become one authorship.** When `same_person` or `link_byline` leaves a person with two authorships of one
  publication, they are joined, as platform v2 joins its bilingual twins. The byline row is kept and given the
  catalogue seq; the catalogue-only row is deleted. This happens in the release only.
- **`not_same_*` records its two sides** (members or authorship refs) when it is made. That lets the release pull
  them apart again, even if a later reading drops one of the ids.
- **What orphans a decision.** Explicit keys and a split's listed members must all be present, or the decision is
  orphaned. Sides recorded as evidence only need one member present on each side; any missing ones are listed in
  the application.
- **Conflicts.** A decision on the same question and subjects as another owner's standing decision is refused when
  it is made. Conflicts across different subjects (e.g. merging two cards someone split) can only show up at
  release, where the earlier decision holds and the owners get notes and a task.
- **"Unsure"** gives the task to someone else and keeps the note. There is no second-key escalation.
- **Card data on split cards.** Citation links and relations stay on the card that keeps the id. On `same_work`
  they move to the surviving card. A split card's title and authors come from its richest member.

More on four of those routes:
- **The crops.**
  - The stem and page are checked against the reading. The file name comes from `pages.page_image_key`, never from
    the request, and it must resolve inside the pages folder. Path traversal gives a 404 or a 422.
  - ALTO line boxes come from the reading's `line_map`, with the ALTO master as a fallback. They are scaled
    image/ALTO per axis: 1812/1808.3, so about 1.002.
  - Crops are cached under `/home/appuser/data/desk/crops/`, which held 2 MB after the walk-through.
  - **Measured:** 0.12–0.19 s for a first crop, under 1 ms from the cache.
- **The before/after view.** A release's summary (top 100, card per full citation, persons, authorships) goes to
  `releases/summaries/<id>.json` (about 0.9 MB, 4 s to make). So the comparison outlives the copy `release.py` prunes.
- **Building a release from the screens.**
  - It runs `release.build_release` in a background thread, one build at a time: a second request gets a 409, and
    so does a `building` row from the command line.
  - The copies on disk are summarised before the build, the new one after it. Then the detectors run on the new
    release. `release.py` itself was not edited.
- **The search index** is built once per state, keyed by its path and mtime, in 0.6 s.

**Sign-in (P1/P2 only).**

- A write that rides on the cookie must also carry `X-Desk-Client: web`. Without it the API answers 403. A page on

**How it works.** `desk/explore.py` declares each entity as one SQL over the state (CTEs + joins) and a list of
columns `(name, expression, type, group, label, where it lives, links to)`. On first use per state (the newest
release copy, else `platform_v2.db`, attached read-only) the six flat tables are materialised into an in-memory
SQLite with a folded `_q` column for quick search; the cache is keyed by the state's path and mtime, so a new
release is picked up at once. The API warms them in a background thread at start-up. Requests can only name
columns, operators and entities from those lists (anything else is a 422), and every value is a bound parameter.
Routes (`desk/explore_routes.py`, included at the end of `api.py`): `GET /explore` (entities, columns, counts),
`/explore/{entity}` (cols, sort, desc, q, f = JSON filters, offset, limit ≤ 500), `/explore/{entity}/groups` (by,
measure), `/explore/{entity}/csv`. The page is `web/pages/explore.tsx`; its strings are `web/lib/strings_explore.ts`.

  web's last rebuild as a triangle), **Results** (dots; milestones as stars), **Promises** (flags at their due time,
  red when overdue), **Alerts** (red ticks from the record; amber ticks for stalled work; overdue promises). Zoom:
  day / week (default: 7 days back, 7 ahead) / month / all — always worked out from *now*, never stored. Tap a bar or
  a mark → a card (side panel; a bottom sheet on a phone): the plain description, status, started / ended / planned
  and slip, last sign of life, outcome, cost, links into the Desk, the write-up's path and when it was last written,
  what it waits on and what follows it, and the sources. Below the chart: *Next, in order* (planned work without
  dates, in `after` order) and the open *Promises*. Phones open on a stacked list (running now, needs you — most
  urgent first, promises, next, live, done in the last 7 days, parked/dropped). Refreshes every 30 s.
- **The data.** One file, `desk/plan/plan.json` (lanes, `items`, `promises`, `markers`, `log`); every item has a
  `source` and, where its times are approximate, an `approx` note. Seeded on 2026-11-02 from `experiments/README.md`,
  each experiment's README and progress notes, file times on the server, git commit times, `docs/STATUS.md`, the Desk
  releases and `desk/project/project.json` (waiting_on_owner, next_steps, timeline): 57 items (extraction 15,
  reconciliation 8, platform & Desk 11, evaluations 5, docs 5, needs you 13; 33 done, 11 waiting on the owner, 9
  planned, 3 running, 1 live), 3 promises, 12 markers. Read live by the
  API on each call (read-only): release ids from `DESK_RELEASES` and its `summaries/` (time from the name, UTC; the
  newest copy is "live"), the live web's `web-live/.next/BUILD_ID` time, each item's README time, and each running
  item's last sign of life (its heartbeat file, else the newest file in its `watch` folder, else its start).
- **Updating it (the lead and agents): `desk/plan_cli.py`**, the only writer; every write takes a lock, re-reads,
  validates, writes a temp file and renames it (atomic), and appends who / when / what to `log`. `PLAN_BY` says who
  is writing.

  ```
  cd experiments/49_correction_desk; export PLAN_BY=agent:lead
  .venv/bin/python -m desk.plan_cli start exp66 "Cited works applied" --lane reconciliation \
      --desc "…one line…" --readme experiments/66_x/README.md --link Librarian=/librarian --watch experiments/66_x
  .venv/bin/python -m desk.plan_cli beat exp66 --note "batch 3 of 9"         # heartbeat: "last seen" on the bar
  .venv/bin/python -m desk.plan_cli finish exp66 --outcome "1,200 decisions applied" [--status live|parked|dropped]
  .venv/bin/python -m desk.plan_cli start rebuild65                          # a planned item starts
  .venv/bin/python -m desk.plan_cli plan gate2-rest "Gate 2: nine more journals" --lane extraction \
      [--start 2026-11-04T09:00 --end +3d] [--after gate2-pilot] [--cost "about $416"]
  .venv/bin/python -m desk.plan_cli set gate2-pilot --clear waits_on --outcome "…"     # edit / remove fields
  .venv/bin/python -m desk.plan_cli needs-you add go-x "Go for X?" --question "…" --urgency soon [--due +2d]
  .venv/bin/python -m desk.plan_cli needs-you resolve go-x --outcome "owner: yes" [--source "conversation …"]
  .venv/bin/python -m desk.plan_cli promise add send-audit "Send the owner the re-audit" --due +6h [--item reaudit]
  .venv/bin/python -m desk.plan_cli promise keep send-audit --outcome "sent"            # or: promise drop …
  .venv/bin/python -m desk.plan_cli add-marker eval "Re-audit: 99.9% in a field" [--at now] [--href /audit]
  .venv/bin/python -m desk.plan_cli list [--status running] | show <id> | check
  ```
  Times: `now`, `+2h`, `-30m`, `+1d`, or ISO (no offset = server time). Titles: at most 6 words / 40 characters.
  Needs-you order: urgency words (urgent/now/today < soon/this week < before/after < when ready < any time), then the
  nearest due; `set <id> --priority 0` overrides.
- **Add item (admins only).** A button on the page: work, something for the owner, or a promise. It posts to
  `POST /desk/api/plan/items`, which calls the same `plan_cli` functions with the admin's actor id (in the item's
  `added_by`, its source and the log). Correctors get 403.
